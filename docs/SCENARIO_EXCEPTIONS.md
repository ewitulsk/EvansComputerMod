# Scenario exceptions

AGENTS.md: a step that genuinely can't be a player-equivalent action is written in
the scenario's notes and here. The standing exception, scripted airship and vehicle
motion (`airship_radio_range` and `airship_radio_return`, the `cell_roaming` cart), needs no entry. Everything else:

| Exception | Scenarios | Why it can't be player-real | Notes |
|---|---|---|---|
| Binary files copied into a computer's folder (`<world>/computer-data/<id>/`) | gui_basics, gui_client_render (arm.gba); phone_gba (arm.gba into the phone's /home); radio_station (WAV songs); video_desktop, video_phone (test_pattern.mp4 into /home/videos); music_stream, music_playlist, music_background, music_duck (the three Tech Village MP3s into the server's /srv/music); video_smooth_under_lag, video_seek_flush, lossy_refine, wall_two_viewers (the same video) | Binary data can't be typed. A player brings ROMs and audio in from outside the game, and copying into the computer's folder is the documented way. | Text files are always typed (Python `shell.write_file`) |
| A malformed UI client opened by the scenario (`Compositor.open` plus an unknown opcode) | gui_basics (control) | No program a player can run sends malformed protocol bytes: the Python `ui` module only sends well-formed messages. | Checks that a broken client loses only its own connection |
| A headless client that draws scenes (`SceneViewerMirror`, display key 9) | gui_client_render | A GameTest server has no client. The real client is covered by `-ClientChecks -ClientSuite gui` (case `gui_client_render`). | All input in the scenario comes from the scenario player through packets |
| Chunk unload and load hooks called directly (`onChunkUnloaded`, `onLoad`) | router_headless, router_ring_tap_*_cut | A GameTest can't unload a test's chunk by walking away | The computers keep running headless; nothing is typed into them while unloaded |
| Typing into a far village ISP router's console (`ispShows`) | router_ring_tap_* | The ISP router is hundreds of blocks away and usually headless. A player would walk there or ssh in. | Read-mostly: `router` / `show ...` / `exit` |
| Second scenario players (`Onlooker`, `Twin`) | phone_visibility, phone_duplicates | Multiplayer behaviour needs a second player, and a GameTest has none | Both act through the same game calls as the first |
| Dimension change by moving the fake player | phone_duplicates | A fake player can't take a portal | — |
| Handheld receiver run without a holder (`HandheldServer.Session.receive` at the listener) | radio_station | Handheld sessions tick per player, and the scenario player never ticks | It is the item's own server-side receiver |
| A scenario player's voice is a test tone (440 / 700 Hz) sent through the voice packet handler (`VoiceServer.onVoice`, `onTalk`) | mic_voice, radio_voice | A scenario player has no microphone or client. What a client would capture is generated and sent through the same server handler as the client's packets. | Everything after the packet (the sound field, Microphones, the handheld's transmitter) is real; the client capture itself is covered by `VoiceClient` and the voice chat mod bridges |
| Handheld radios ticked by the scenario (`HandheldServer.tickPlayer` for the talker and the listener) | radio_voice | Handheld sessions tick per player, and scenario players never tick | It is the code the player tick runs: the radios are held, switched on by right-click and tuned through the tuning screen's packet handler |
| Probe apps copied into a phone's app folder; permissions set in the app manager | phone_gui, phone_background, phone_gba, background_pocket, background_duck, background_limit, background_wake; desktop_tray (on a Terminal) | No repository or package carries the `phonetest` probes (the phone's Terminal could install one with `pkg`, but there is none to install), and the phone has no settings page for these toggles | — |
| The phone holder moved along a fiber chord by script (12 blocks a second of real time, beside the line at head height); the cell sites within 10 chunks of the phone (and the phone's own chunk) kept ticking | cell_tech_village (ride) | The scenario player can't walk or ride by itself (it never ticks), and the client-check server runs a 3-chunk simulation distance to stay fast; a player's own ticket would tick 10 chunks on a default server (only the sites in it are ticked, so the suite needn't generate a 21-chunk-wide band) | Like the standing vehicle exception: only the motion is scripted; the phone, its cells, handovers and the core are real |
| A Tech Village placed at its planned site (`TechVillageLocator.placeForTest`, what `/place structure` does) and the ring's infrastructure computers started (`WorldNetwork.boot`, what `WorldNetwork.start` does when a normal server starts) | browser_village, browser_dns, browser_home (GameTest only; in a normal world they use the nearest generated village and the running ring) | A GameTest world is created with structures off, and GameTest servers skip starting the Tech Village infrastructure | The house router and PC are started by the player opening their screens; everything typed and clicked is the player's |
| The upload file picker: the player's pick is armed with `UploadBackend.simulatePick` (a file in `<server>/scenario-uploads/`), and the server sends it through the sidecar's own Begin/Chunk/End handlers | upload_terminal, upload_files_app, upload_phone | The scenario player has no game, so there is no system file picker to click and no client to send the bytes. The real picker and network path are covered by `-ClientChecks -ClientSuite upload` | The player's steps are real: typing `upload` (and the Python and Lua programs), clicking Upload in Files |
| Simulated network latency: a client in the server's JVM (`testing/LaggyViewer`, a test viewer of the Terminal's display and listener of its Speaker) whose packets arrive after a set latency and jitter, in order, with acks taking the latency back | video_smooth_under_lag, video_seek_flush, lossy_refine, wall_two_viewers (two clients), interactive_latency | A player can't add latency to their own connection, and a GameTest server has no client. The client side is the real client code (`ClientPlayout`, `ClientUiScenes`, the packet codecs) fed the real packets the display pump sends | Everything the player does is real: blocks placed, `gui`, Files, clicks, keys, `/tick rate`; the latency is in the scenario notes |
| Compressed timers: the background refresh interval (minutes to 2-3 s) and the AP inactivity timeout (300 s to 5 s, GameTest hook) | phone_background, cell_chat; wifi_5ghz (GameTest only) | The real values don't fit a one-minute test, and the config's minimum for refresh is 1 minute | — |
| "The internet" is a one-page web server the internet sidecar runs on the host machine (`InternetUplinkProvider.openTestSite`), and the sidecar's LAN block lets that one address and port through while it is open | router_internet | A test can't depend on a public website being up and reachable from the test machine, and the page has to be outside the game. A player would curl a real site (manual mode can) | The client still cables up, types its address and `curl`s through the real host socket proxy. The control (another port on the same LAN address) shows the LAN block. |

Allowed without an entry, because each is a real action a player or operator takes:

- Operator commands with cheats on: `/forceload`, `/gamerule`, `/summon`, `/give`, the diagnostic `/ecm radio link`, and the operator's fiber cut `/ecm net cut|repair A B` (dns_resilience, dns_register: the chords are kilometres long, and the command is the documented way to cut one).
- Server-config values an operator edits in `serverconfig`: `PhoneConfig.override`, and `EcmConfig.setUiClientRendering` `EcmConfig.setDisplayAllowLossy` and `EcmConfig.setAppsMaxBackgroundApps` (background_limit), which write the file.
- The vanilla `/tick rate` command (video_smooth_under_lag, interactive_latency slow the server to 5 ticks a second).
- Vanilla terrain and filled chests set with setBlock, like `/fill` or a creative build.
- Creative inventory moves and hotbar selection.
- Packet handlers' server bodies run with the scenario player as sender: AP Configure, phone hotkeys, controller input, and the phone's display prefs (`PhoneServer.setPrefs`).
